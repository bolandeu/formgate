# Pro: запуск в Docker Compose

Pro — один проект Docker Compose: сервис `web` (nginx и php-fpm; на порту форм отдаёт только `/f/<ключ>` и `/health`, на своём порту — admin API `/admin`, раздел 8) и сервис `worker` (доставка заявок, `restart: unless-stopped`). SQLite и файлы проектов лежат на томах `data` и `projects`. В образах нет данных и секретов.

## 1. Установка и обновление скриптом

Скрипт `install.sh` из корня репозитория ставит Pro на сервер с Docker одной командой:

```sh
curl -fsSL <адрес>/install.sh | sh -s -- --domain example.ru --port 8095
```

Что делает установка, по шагам:

```
Docker и Compose v2? ──нет──> отказ, что поставить; ничего не записано
        │
тег: --version или высший vX.Y.Z; нет такого ──> отказ со списком последних тегов
        │
блокировка <папка>/.install/lock; занята ──> отказ
        │
git checkout тега ─> .env (если его нет) ─> docker compose build, up -d ─> ждёт GET /health
        │
печатает команду project:create для первого проекта
```

- Без терминала (например, в CI) или с `--yes` скрипт ничего не спрашивает. Нет обязательного значения — отказ с именем флага (`--port`).
- `.env` пишется из `.env.example` с ответами, права 600. Пустые ключи `*_SECRET` и пустой `FORMGATE_ADMIN_KEYS` получают случайное значение. `FORMGATE_ADMIN_PORT` — `127.0.0.1` и порт после `--port`. Существующий `.env` повторный запуск не трогает; тома с данными скрипт не удаляет никогда.
- `.install/tag` — установленный тег, `.install/previous-tag` — тег до последнего обновления.

Флаги:

| Флаг | Что задаёт | По умолчанию |
|---|---|---|
| `--dir <папка>` | папка установки (checkout репозитория и `.env`) | `/opt/formgate` |
| `--repo <url>` | git-репозиторий исходников | репозиторий прежней установки, иначе `https://github.com/bolandeu/formgate.git` |
| `--version vX.Y.Z` | тег | высший тег `vX.Y.Z` |
| `--ref <ref>` | любой ref (коммит, ветка) без проверки тега — для CI и проверок; вместе с `--version` — отказ; `--update` его не учитывает | нет |
| `--port <порт>` | порт web на `127.0.0.1` (`FORMGATE_WEB_PORT`); admin API — следующий порт (`FORMGATE_ADMIN_PORT`) | обязателен для нового `.env` |
| `--domain <домен>` | `FORMGATE_DOMAIN` | нет |
| `--tls` | профиль `tls` (`COMPOSE_PROFILES=tls`), нужен `--domain`; описание — `docs/pro-tls.md` | выключен |
| `--alert-bot-token`, `--alert-chat-id` | бот оповещений оператора | пусто: оповещения только в логе |
| `--health-timeout <секунды>` | сколько ждать ответа `/health` | 120 |
| `--yes` | не задавать вопросов | вопросы, если есть терминал |
| `--update` | обновление | установка |

Обновление:

```sh
sh /opt/formgate/install.sh --update --dir /opt/formgate
```

`--update` берёт высший тег (или `--version`), записывает текущий тег в `.install/previous-tag`, собирает и поднимает новый, ждёт `/health`. Если текущий тег и есть высший (или заданный `--version`), скрипт ничего не меняет. Если `/health` не ответил за `--health-timeout`, скрипт возвращает прежний тег, собирает и поднимает его и завершается с ошибкой, называя тег, который не поднялся. Блокировка осталась после убитого запуска — удалите папку `.install/lock`, когда другой запуск не идёт.

Разделы 2–3 ниже — ручная установка, запасной путь без скрипта.

## 2. Подготовка (вручную)

```sh
cp .env.example .env
```

Заполните `.env`: переменные описаны в самом файле. Реальные значения лежат только в `.env`, в git он не попадает. Порт `FORMGATE_WEB_PORT` обязателен: без него `docker compose` остановится с ошибкой. Значение — `адрес:порт`; по умолчанию `127.0.0.1:8095`, то есть порт виден только на самом сервере. Docker обходит firewall хоста, поэтому голый порт (`8095`) открыл бы его на всех адресах. Другой адрес оператор задаёт в `.env` явно, например `0.0.0.0:8095` или адрес частной сети. Папки данных и проектов задаёт `compose.yaml` рядом с томами; в `.env` их не задают. Настройки воркера и оповещений — раздел 4, «Очередь, повторы, хранение и оповещения».

## 3. Запуск (вручную)

Запуск:

```sh
docker compose up -d
```

Разработка: исходники смонтированы (файл `compose.dev.yaml`). Раскомментируйте в `.env` строку `COMPOSE_FILE=compose.yaml:compose.dev.yaml`, затем снова `docker compose up -d`.

Правка PHP видна без пересборки. Образ пересобирается командой `docker compose build` после правки `composer.json`.

## 4. Первый проект

Проектами управляет CLI внутри контейнера: `docker compose exec web php bin/formgate <команда>`. Файлы проектов вручную не пишут.

Создать проект: имя, первый домен и первый канал. Здесь канал — email через SMTP-сервер: хост и порт SMTP даёт администратор сервера, в репозитории адрес не задан. Параметры канала — `-o имя=значение`; значение в `[..]` или `{..}` читается как JSON. Какие опции есть у каждого типа канала — `docs/lite-setup.md`, раздел 7.

```sh
docker compose exec web php bin/formgate project:create Dev localhost email \
  -o 'to=["operator@example.test"]' \
  -o 'methods=[{"type":"smtp","host":"<SMTP_HOST>","port":1025,"encryption":"none","from":"formgate@example.test"}]'
```

Команда печатает `Key: <ключ>` и `Form address: /f/<ключ>`. Ключ — 16 случайных латинских букв и цифр; имя проекта по ключу не угадать. Канал без обязательной опции команда отказывает с именем поля, проект не создаётся.

Остальные команды проектов (`docker compose exec web php bin/formgate <команда>`):

- `project:show [ключ]` — один проект (секреты скрыты) или список всех.
- `project:set <ключ> <путь> <значение>` — одна настройка. Путь — один из `project.thank_you_url`, `project.error_url`, `project.duplicate_window_seconds`, `project.rate_limit.requests`, `project.rate_limit.window_seconds`, `project.required`, `project.require_token`, `project.token_min_seconds`, `project.token_max_seconds` или `limits.<имя>` (например, `limits.max_fields`). Пример: `project:set <ключ> project.thank_you_url https://site.ru/spasibo`. Срок хранения в Pro общий для всех проектов (`FORMGATE_RETENTION_DAYS`, раздел 4, «Очередь, повторы, хранение и оповещения»); `project.retention_days` в Pro `project:set` отклоняет.
- `project:domain:add <ключ> <домен>` — разрешить ещё один домен.
- `project:domain:remove <ключ> <домен>` — убрать домен.
- `project:channel:add <ключ> <тип> -o ...` — добавить канал (`telegram`, `email`, `bitrix24`).
- `project:channel:change <ключ> <номер> -o ...` — изменить параметры канала; первый номер — 1.
- `project:channel:remove <ключ> <номер>` — убрать канал. Каналы после него получают меньшие номера. Поэтому команда отказывает, если частный случай ссылается на этот канал или на канал после него по номеру: она называет случай, файл не меняется. Сначала уберите или измените случай.
- `project:self-check <ключ> [--send]` — проверить каналы (и ключ подписи метки времени, когда проверка включена); `--send` шлёт тестовое сообщение в каждый канал.
- `project:delete <ключ> [--yes]` — удалить проект; без `--yes` команда спросит.

### Частные случаи

Частный случай — условие и каналы. Заявка, которая подошла под случай, идёт только в его каналы; остальные идут по маршруту по умолчанию (во все каналы). Работает первый подошедший случай по порядку списка. Обязательные поля проекта и случая проверяются всегда, форма может только добавить свои.

- `project:case:add <ключ> [--name <имя>] [--form <форма>] [--field <поле> --equals <значение>] --channel <номер или имя> [--required <поле>]` — добавить случай в конец списка. Нужно хотя бы одно условие; `--channel` и `--required` можно повторять. Значения сравниваются без учёта регистра и пробелов по краям.
- `project:case:list <ключ>` — случаи по порядку: номер, имя, условия, каналы, обязательные поля.
- `project:case:move <ключ> <номер> <новое место>` — переставить случай; порядок задаёт приоритет.
- `project:case:remove <ключ> <номер>` — убрать случай; следующие получают меньшие номера.

Обязательные поля всего проекта задаёт `project:set <ключ> project.required email,phone`: список через запятую.

Неверный канал или условие команда отказывает с названием поля, файл проекта не меняется.

Пример: заявки формы `vacancy` идут только на почту отдела кадров, второй канал проекта.

```sh
docker compose exec web php bin/formgate project:case:add <ключ> --name vacancies --form vacancy --channel 2 --required email
docker compose exec web php bin/formgate project:case:list <ключ>
# #1 vacancies | form=vacancy | channels 2 | required email
```

`failed` и `spam:list` показывают маршрут каждой заявки: `route default` или `route case #1 vacancies`. Для записи спам-лога это маршрут по настройкам проекта сейчас, по которому её доставит `spam:release`; если файл проекта не загружается, `spam:list` показывает `route unknown`.

Заявки, которые не доставлены:

- `failed` — список недоставленных заявок: `#<id> project <ключ> received <время> route <маршрут>` и строка на каждый канал с причиной.
- `failed:retry [id] [--project=<ключ>]` — повторить заявку или все заявки проекта в каналы, которые их не приняли.

Воркер — команда `worker` (`php bin/formgate worker`), его запускает сервис `worker` Compose. `worker --once` делает один проход по заявкам, которым пора, и завершается.

### Очередь, повторы, хранение и оповещения

Pro отвечает посетителю «отправлено», когда заявка сохранена в очереди, даже если канал сейчас не работает. Воркер берёт заявки, которым пора, и шлёт каждую в каналы маршрута. Настройки воркера — переменные `.env` (список и значения по умолчанию — `.env.example`):

| Переменная | Что задаёт |
| --- | --- |
| `FORMGATE_WORKER_PAUSE_SECONDS` | пауза цикла воркера между проходами |
| `FORMGATE_REPEAT_SCHEDULE_SECONDS` | паузы повторов через запятую; по умолчанию 1 мин, 5 мин, 15 мин, 1 ч, 3 ч, 12 ч, 24 ч |
| `FORMGATE_CHANNEL_DOWN_AFTER_FAILURES` | сколько неудач подряд делают канал «упавшим» (3) |
| `FORMGATE_RETENTION_DAYS` | через сколько дней воркер удаляет заявки и записи спам-лога всех проектов (30) |
| `FORMGATE_RETENTION_INTERVAL_SECONDS` | как часто воркер чистит старое (раз в час) |
| `FORMGATE_SQLITE_BUSY_TIMEOUT_SECONDS` | сколько процесс ждёт другого, который пишет в базу |

**Повторы.** Повтор идёт в каждый канал отдельно: канал, который уже принял заявку, второй раз её не получает. Первая пауза считается от первой неудачи, каждая следующая — от неудачи предыдущего повтора. После последней паузы заявка получает статус `not_delivered` (команда `failed` её показывает) и оператор получает оповещение. Вручную заявку повторяет `failed:retry`.

**Оповещения.** Один бот Telegram на весь Pro: `FORMGATE_ALERT_BOT_TOKEN` и `FORMGATE_ALERT_CHAT_ID` (`FORMGATE_ALERT_API_URL`, `FORMGATE_ALERT_TIMEOUT_SECONDS` — адрес API и время ожидания). Бот шлёт одно сообщение при каждом из трёх событий: канал проекта «упал» (неудачи подряд на любых заявках), канал «поднялся» (первая удачная доставка), заявка не доставлена после последнего повтора. Сообщение называет ключ проекта и канал, данных заявки в нём нет. Без токена оповещения только пишутся в лог.

**Что хранит запись.** Заявка в очереди и запись спам-лога хранят поля, которые прислал сайт, время получения, маршрут и четыре значения, которые шлюз записывает сам: `request_id`, `ip`, `user_agent`, `origin_host` (описание — `docs/lite-setup.md`, раздел 6). В канал они не уходят. Запись, сделанная до появления этих значений, хранит их пустыми.

## 5. Проверка (вручную)

Проверку запускают на любом хосте с Docker и Compose v2, где стоит Pro. Адреса ниже — для самого хоста; с другой машины подставьте имя или адрес хоста вместо `localhost`.

1. Создать проект командой из раздела 4 и записать ключ: `KEY=<ключ из вывода>`.
2. Отправить форму на порт 8095:

   ```sh
   curl -i -X POST http://localhost:8095/f/$KEY \
     -H 'Origin: http://localhost' -H 'Content-Type: application/json' -H 'Accept: application/json' \
     -d '{"__form":"callback","name":"Анна","phone":"+7 900 123-45-67","consent":"1"}'
   ```

   Ответ: `200` и `{"ok":true}`.

3. Здоровье: `curl -i http://localhost:8095/health` — ответ `200` и `{"ok":true}`. Воркер отмечается в течение `FORMGATE_WORKER_PAUSE_SECONDS`; сразу после старта `/health` может несколько секунд отвечать `503` и `{"ok":false,"check":"worker","error":"…"}`. Поле `check` — `database` (база не пишется) или `worker` (воркер не отмечался дольше `FORMGATE_WORKER_HEARTBEAT_MAX_AGE_SECONDS`).
4. Письмо: открыть почтовый ящик канала или веб-интерфейс тестового SMTP-сервера (например, Mailpit) — в списке письмо с заявкой.

`docker compose ps` показывает `web` как `healthy`, когда `/health` отвечает `200`. У `worker` проверки здоровья нет: его работу показывает `/health`.

## 7. Метка времени и спам-лог

Метка времени (описание — `docs/integration.md`, раздел 6) работает в Pro для каждого проекта отдельно. Клиент берёт метку запросом `GET /f/<ключ>?token` с домена проекта и шлёт её в заявке полем `__token`. Неизвестный ключ получает `404 project_not_found`.

**Включить проверку.** По умолчанию она выключена и включается настройкой `project.require_token` проекта; пороги возраста метки — `project.token_min_seconds` и `project.token_max_seconds` (описание — `docs/integration.md`, раздел 6). Включить: `project:set <ключ> project.require_token true` (также `on`/`off`, `1`/`0`; другое значение команда отклоняет, называя `true`/`false`). Пороги в целых секундах: `project:set <ключ> project.token_min_seconds 10` и `project:set <ключ> project.token_max_seconds 3600`; минимум должен быть меньше максимума, иначе команда отказывает и файл не меняется. `project:show <ключ>` показывает значения. С включённой проверкой заявка без действительной метки не доставляется и попадает в спам-лог с причиной (`token_missing`, `token_unavailable`, `bad_signature`, `too_fast`, `expired`, `reused`). Метка одного проекта в другом даёт `bad_signature`.

**Секрет.** Метки подписывает секрет `FORMGATE_TOKEN_SECRET` из `.env`, один на все проекты. `install.sh` записывает в него случайное значение при первой установке; повторный запуск и `--update` его не меняют. Менять секрет вручную не нужно: после смены все выданные метки становятся недействительными, и заявки посетителей, открывших форму раньше, попадают в спам-лог с причиной `bad_signature`. Без секрета у проекта с включённой проверкой запрос метки отвечает `server_error`, а `project:self-check <ключ>` печатает `fail Time token: ... FORMGATE_TOKEN_SECRET is not set`. Секрет в вывод команд не попадает.

**Спам-лог.** Две команды (`docker compose exec web php bin/formgate <команда>`):

- `spam:list` — записи спам-лога всех проектов: `#<id> project <ключ> received <время> reason <причина> route <маршрут>` и в следующей строке поля заявки (секретные поля скрыты, как в `project:show`).
- `spam:release <id>` — отправить запись в доставку. Запись с причиной метки (`token_unavailable` и другие причины метки) становится обычной заявкой в очереди и уходит из спам-лога; воркер доставляет её в каналы проекта так, как её отправил посетитель, со служебными полями (`__subject`, `__replyto`, `__required`, `__redirect`). Запись с другой причиной (`honeypot`, `rate_limit` и т. д.) команда отказывает с названием причины, неверный id — с `not found`; в обоих случаях ничего не меняется и код выхода не ноль.

Записи, сделанные до этой версии, не хранят служебные поля: после `spam:release` они доставляются с значениями по умолчанию.

## 8. Admin API

Admin API — JSON API для внешнего инструмента: он создаёт, показывает, меняет и удаляет проекты по тем же правилам, что CLI. API слушает свой порт, не порт форм: на порту форм `/admin` отвечает `404`.

**Порт.** `FORMGATE_ADMIN_PORT` в `.env` — `адрес:порт`, который Compose отображает на порт admin API в контейнере `web`. По умолчанию `127.0.0.1:8096`: порт виден только на самом сервере. TLS на этом порту нет, поэтому его не открывают в интернет; другой инструмент ходит через SSH-туннель или частную сеть. Старый `.env` без этой строки получает значение по умолчанию.

**Ключи.** `FORMGATE_ADMIN_KEYS` в `.env` — список ключей через запятую. Запрос с заголовком `Authorization: Bearer <ключ>` с любым ключом из списка обслуживается. Без заголовка или с чужим ключом — `401` и `{"ok":false,"code":"unauthorized"}`. Пустой список выключает API: любой путь `/admin` отвечает `404`. `install.sh` при новой установке записывает один случайный ключ; повторный запуск и `--update` его не меняют. Ключи в ответы не попадают; секреты каналов в ответах скрыты (`***`), как в `project:show`.

**Смена ключа без перерыва.**

1. Добавить новый ключ через запятую: `FORMGATE_ADMIN_KEYS=<старый>,<новый>`, затем `docker compose up -d`.
2. Перевести инструмент на новый ключ.
3. Убрать старый ключ: `FORMGATE_ADMIN_KEYS=<новый>`, затем `docker compose up -d`.

**Вызовы.** Ответ — JSON. Проект в ответе: `{"key", "external_id", "name", "domains", "channels", "form_path":"/f/<ключ>"}`.

- `POST /admin/projects` с телом `{"external_id", "name", "domain", "channel":{"type", "options"}}` — создать проект. `external_id` — id проекта во внешнем инструменте, он уникален в реестре. Новый `external_id` — `201` и `{"ok":true,"project":{...}}`. Существующий `external_id` — `200` с тем проектом, ничего не меняется, даже если имя или канал другие: повтор запроса безопасен. Проверки те же, что у `project:create`; неверные данные — `422` и `{"ok":false,"code":"invalid","error":"<причина>"}`, проект не создаётся.
- `GET /admin/projects/<ключ>` — проект по ключу.
- `GET /admin/projects?external_id=<id>` — проект по `external_id`.
- `POST /admin/projects/<ключ>/domains` с телом `{"domain"}` — добавить домен. `DELETE /admin/projects/<ключ>/domains/<домен>` — убрать домен; последний домен убрать нельзя.
- `POST /admin/projects/<ключ>/channels` с телом `{"type", "options", "name"?}` — добавить канал; он получает следующий номер. `PATCH /admin/projects/<ключ>/channels/<номер>` с телом `{"options"}` — изменить канал: новые опции накладываются на старые, как в `project:channel:change`. `DELETE /admin/projects/<ключ>/channels/<номер>` — убрать канал; последний канал и канал, который использует частный случай, убрать нельзя.
- `DELETE /admin/projects/<ключ>?confirm=true` — удалить проект, как `project:delete`. Без `confirm=true` — `400` и `{"ok":false,"code":"confirm_required"}`, проект остаётся.
- `POST /admin/projects/<ключ>/selfcheck` с телом `{"send": true|false}` — самопроверка, как `project:self-check`. Ответ: `{"ok":true,"findings":[{"level":"ok|fail","label","detail"}]}`. Без отправки каждый канал только собирается из настроек; с `send: true` через каждый канал уходит одно тестовое сообщение.

Каждое изменение отвечает `200` и проектом (секреты скрыты). Отказ — `422` и `{"ok":false,"code":"invalid","error":"<причина>"}`, ничего не меняется. Два изменения одного проекта одновременно идут друг за другом под блокировкой реестра, как в CLI: ни одно не теряется.

Нет проекта — `404` и `{"ok":false,"code":"project_not_found"}`. Неизвестный путь — `404`. У проектов, созданных CLI, `external_id` равен `null`.

```sh
ADMIN_KEY=<ключ из FORMGATE_ADMIN_KEYS>
curl -i -X POST http://localhost:8096/admin/projects \
  -H "Authorization: Bearer $ADMIN_KEY" -H 'Content-Type: application/json' \
  -d '{"external_id":"site-1","name":"Site 1","domain":"site1.ru","channel":{"type":"telegram","options":{"bot_token":"<токен бота>","chat_id":"<id чата>"}}}'
curl -i -H "Authorization: Bearer $ADMIN_KEY" 'http://localhost:8096/admin/projects?external_id=site-1'
```
