# Подключение формы к Formgate

Документ для разработчика сайта: как сделать форму, чтобы шлюз принял заявку, отсёк спам и вернул понятный ответ.

Проверку заполненности и формата полей сайт делает сам, в браузере. Шлюз принимает любые поля и на сервере проверяет только то, что описано ниже (раздел 8): проверку в браузере бот обходит.

## 1. Куда отправлять

| Версия | Адрес |
| --- | --- |
| **Pro** | `POST https://<хост-шлюза>/f/<ключ-проекта>` |
| **Lite** | `POST` на файл обработчика на том же сайте, например `/formgate/submit.php` |

Ключ проекта публичный, его выдаёт оператор. Его можно держать в HTML.

Lite кладётся в любую папку рядом со статикой сайта: `public_html`, `www`, корень сайта на VPS. Он работает на обычном виртуальном хостинге и на VPS, если там есть PHP.

И Lite, и Pro принимают заявки только с доменов проекта (заголовок `Origin`, а без него `Referer`). Запрос с чужого домена получает `403 origin_not_allowed`.

**CORS** включён всегда, отключить его нельзя. Lite и Pro отвечают на preflight (`OPTIONS`) и отдают `Access-Control-Allow-Origin` только для доменов проекта, поэтому `fetch` с чужого сайта браузер заблокирует.

## 2. Формат запроса

- Кодировка — UTF-8.
- Поддерживаются:
  - `application/x-www-form-urlencoded` — обычная HTML-форма;
  - `multipart/form-data` — файлы не принимаются, файловые поля отбрасываются;
  - `application/json` — плоский объект `{"name": "…", "phone": "…"}`.
- Имена полей любые, латиницей. Поле со множеством значений (`interests[]`) приходит в каналы через запятую.
- Ограничения:
  - не больше 100 полей;
  - не больше 10 000 символов в одном значении;
  - поля `meta_` считаются отдельно (раздел «Поля аналитики» ниже);
  - тело запроса не больше 100 КБ. Больше — `413 payload_too_large`.

## 3. Служебные поля

Поля с именем на `__` управляют обработкой и **не** попадают в заявку. Неизвестные `__`-поля игнорируются. Не называйте так обычные поля.

| Поле | Зачем | Пример |
| --- | --- | --- |
| `__form` | Имя формы. По нему оператор задаёт частный случай в настройках проекта, например «вакансии — на почту HR»: заявка этой формы уходит только в каналы случая, остальные — по маршруту по умолчанию, во все каналы. Имя сравнивается без учёта регистра и пробелов по краям. | `vacancy` |
| `__subject` | Тема письма в email-канале. | `Заявка с лендинга` |
| `__replyto` | Имя поля с email посетителя для Reply-To. По умолчанию `email`. | `contact_email` |
| `__required` | Какие поля формы обязательны, через запятую (в JSON — массив). Шлюз проверяет, что они пришли и не пустые. | `phone,consent` |
| `__redirect` | Куда отправить посетителя после отправки без JS. Только URL на домене проекта, иначе игнорируется. | `https://site.ru/spasibo` |
| `__token` | Метка времени от клиента formgate (раздел 6). Руками не заполняется. | — |
| `__token_unavailable` | `1`, если клиент не смог получить метку времени (раздел 6). Руками не заполняется. | `1` |

Адрес получателя письма задаёт оператор. Через форму его передать нельзя.

С каждой заявкой шлюз сам записывает ещё четыре значения: `request_id`, `ip`, `user_agent`, `origin_host` (раздел 6 `docs/lite-setup.md`). Их не присылает сайт, и в каналы они не попадают.

### Поля аналитики (`meta_`)

Поле, имя которого начинается с `meta_`, — поле аналитики заявки (префикс фиксирован). Сайт может прислать любые: `meta_utm_source`, `meta_page`, `meta_referrer`, `meta_yclid`. Заявка хранит их отдельно от полей посетителя, но целиком: они остаются в сохранённой заявке и в спам-логе.

- Лимиты: не больше 50 полей `meta_` (`limits.max_meta_fields`), до 2000 символов в значении (`limits.max_meta_value_length`). Больше — `413 payload_too_large`. Лимиты `max_fields` и `max_value_length` считают только остальные поля. В Pro лимиты меняет `project:set`, как и другие.
- Telegram и email: сначала строки посетителя и строка согласия, затем пустая строка и блок `Источник: <utm_source> / <utm_medium> / <utm_campaign>`, `Страница: <meta_page>`, `Реферер: <meta_referrer>`. Строка блока, у которой нет ни одного поля, пропускается; без этих полей блока нет. Остальные поля `meta_` в сообщение не попадают.
- Bitrix24: `meta_utm_source`, `meta_utm_medium`, `meta_utm_campaign`, `meta_utm_content`, `meta_utm_term` попадают в `UTM_SOURCE`, `UTM_MEDIUM`, `UTM_CAMPAIGN`, `UTM_CONTENT`, `UTM_TERM`. Каждое другое поле `meta_` — строкой `имя: значение` в `SOURCE_DESCRIPTION`. В `COMMENTS` только поля посетителя. Поле `meta_`, названное в `map`, попадает только в своё поле лида.

## 4. Согласие на обработку персональных данных (152-ФЗ)

Проверка согласия включена всегда, отключить её нельзя.

- В форме обязательная галочка `<input type="checkbox" name="consent" value="1" required>`. Рядом ссылки на согласие и на политику обработки ПД.
- Значение должно быть ровно `1`. Значение браузера по умолчанию `on` (галочка без `value`) не принимается.
- Имя поля по умолчанию `consent`, оператор может задать другое.
- Без галочки шлюз отвечает `422 consent_required`.
- В каждый канал вместе с заявкой уходит строка «Согласие на обработку ПД: дано ДД.ММ.ГГГГ ЧЧ:ММ».

## 5. Honeypot — обязательно

Honeypot — поле-ловушка. Человек его не видит и оставляет пустым, бот заполняет. Заявка с заполненной ловушкой отбрасывается молча: бот получает обычный «успех».

Имя ловушки задаёт оператор в настройках проекта. По умолчанию — `website`. Требования:

1. Имя похоже на обычное поле (`website`, `company`, `fax`). Не `honeypot`, не `__…`: умные боты пропускают подозрительные имена.
2. Тип — `text`, **не** `hidden`: боты знают, что `hidden` трогать не надо.
3. Поле прячет CSS-класс за краем экрана. Не `display:none` в атрибуте `style`: такие поля боты тоже распознают.
4. `tabindex="-1"` и `autocomplete="off"` — чтобы туда не попали ни клавиатурой, ни автозаполнением браузера.
5. Атрибуты-исключения для менеджеров паролей: `data-1p-ignore`, `data-lpignore="true"`, `data-bwignore`, `data-protonpass-ignore`, `data-form-type="other"`. 1Password, LastPass, Bitwarden и Proton Pass игнорируют `autocomplete="off"` и иначе заполнят ловушку за человека.
6. Обёртка с `aria-hidden="true"` — чтобы скринридер не предложил поле незрячему посетителю.
7. В форме ровно одно поле с этим именем.

```html
<style>
  .fg-hp { position: absolute; left: -9999px; width: 1px; height: 1px; overflow: hidden; }
</style>

<div class="fg-hp" aria-hidden="true">
  <label for="fg-website">Не заполняйте это поле</label>
  <input type="text" id="fg-website" name="website" tabindex="-1" autocomplete="off" value=""
         data-1p-ignore data-lpignore="true" data-bwignore data-protonpass-ignore data-form-type="other">
</div>
```

## 6. Клиент formgate — по желанию

Без клиента форма работает: honeypot, проверка домена и лимит частоты не требуют JS. Клиент добавляет:

- **Метку времени.** Клиент при привязке к форме получает от шлюза подписанную метку и отправляет её в поле `__token`. С включённой проверкой шлюз отбрасывает заявку без метки, отправленную раньше нижнего порога или позже верхнего. Метка одноразовая: клиент берёт новую после каждой отправки, после возврата на страницу кнопкой «Назад» (`pageshow`) и если текущей больше часа. Если посетитель отправил форму раньше `min_seconds`, клиент ждёт остаток сам. Если метку не удалось получить за ~10 секунд, клиент шлёт `__token_unavailable=1`.
- **Отправку без перезагрузки страницы** и события для показа результата.
- **Офлайн-очередь.** Если ответ шлюза не пришёл (нет сети), клиент хранит заявку в `localStorage` посетителя и отправляет её при восстановлении сети и при следующем заходе на сайт, до 7 суток. Форма получает событие `formgate:error` с кодом `queued_offline`.

> Если оператор включил проверку метки, **все** формы проекта должны быть подключены через клиент. Заявка без `__token` считается ботом и молча отбрасывается.

### Метка времени

**Получение.** `GET <адрес формы из раздела 1>?token` с домена проекта отвечает `200`:

```json
{ "token": "1772355600.q3J….Xb4…", "min_seconds": 5 }
```

- `token` — одноразовая метка: время выдачи, случайный id и подпись HMAC-SHA256 (base64url). Клиент не разбирает её, а отправляет как есть.
- `min_seconds` — нижний порог: раньше этого числа секунд после выдачи заявку отправлять нельзя.

CORS — как у отправки заявки. С чужого домена ответ `403 origin_not_allowed` (раздел 8). Ответ не кэшируется (`Cache-Control: no-store`).

**Отправка.** Клиент кладёт метку в служебное поле `__token`. Если метку получить не удалось, клиент отправляет `__token_unavailable=1` без `__token`. Оба поля не попадают в заявку и в каналы.

**Настройки проекта** (Lite — раздел `project` файла настроек):

| Настройка | По умолчанию | Что делает |
| --- | --- | --- |
| `require_token` | `false` | Включает проверку метки. Выключена — заявки проходят, как без клиента. |
| `token_min_seconds` | `5` | Нижний порог возраста метки, секунды. |
| `token_max_seconds` | `7200` | Верхний порог возраста метки, секунды (2 часа). |

**Проверка.** С включённой проверкой заявка без действительной метки получает обычный ответ «успех» (раздел 8), не доставляется и попадает в спам-лог с причиной:

| Причина | Когда |
| --- | --- |
| `token_missing` | Нет `__token` |
| `token_unavailable` | Нет `__token`, но есть `__token_unavailable=1`: клиент не смог получить метку. Спам-лог хранит все поля заявки |
| `bad_signature` | Подпись не сходится: метку подделали, изменили или выдал другой шлюз |
| `too_fast` | Отправлена раньше `token_min_seconds` после выдачи |
| `expired` | Отправлена позже `token_max_seconds` после выдачи |
| `reused` | Метку уже использовала другая заявка |

**Ключ подписи.** Lite создаёт ключ сам при первом запросе метки и хранит рядом со своим хранилищем: над корнем сайта, иначе в защищённом файле в папке Lite. По HTTP ключ не отдаётся. Самопроверка показывает, включена ли проверка, есть ли ключ и пороги; сам ключ она не выводит.

Клиент есть в трёх видах. Логика у них одна. Подробности установки и привязки — в `README.md`, раздел «Три способа привязать форму».

### npm-пакет — для сайтов на сборщиках (Vite, webpack и др.)

Сборщик кладёт клиент в бандл сайта. Это нужно для сайтов с Content Security Policy: внешний скрипт с хоста шлюза CSP заблокирует. Для Astro удобнее интеграция из следующего раздела.

```js
import { bindForm } from 'formgate/client';

for (const form of document.querySelectorAll('form[data-formgate]')) bindForm(form);
```

Если сайт меняет страницы без перезагрузки (Astro `ClientRouter`), привязывайте клиент к каждой новой форме после перехода (`astro:page-load`) и не дважды к одной. Метку времени клиент берёт при привязке к форме, а не при загрузке скрипта.

### Astro-интеграция — для любого сайта на Astro

`formgate/astro` делает всё сама: кладёт Lite в сборку (или пропускает его, если задан адрес Pro), привязывает клиент к формам с `data-formgate`, в том числе после переходов `ClientRouter`. Адрес обработчика она отдаёт для атрибута `action` формы.

### Файл `formgate.js` — для статических лендингов без CSP

Файл лежит в папке Lite рядом с `submit.php`, поэтому Lite отдаёт его сам. Pro его не отдаёт (на порту форм только `/f/<ключ>` и `/health`): скопируйте `formgate.js` из пакета (`formgate/lite/formgate.js`) на свой сайт.

Подключение:

```html
<!-- Lite -->
<script src="/<папка-шлюза>/formgate.js" defer></script>
<!-- Pro: файл лежит на самом сайте -->
<script src="/formgate.js" defer></script>

<form action="…адрес из раздела 1…" method="post" data-formgate>
  …
</form>
```

Файл обрабатывает только формы с атрибутом `data-formgate`.

### События

Все виды клиента после ответа генерируют событие на форме. Блок `[data-form-status]` в форме получает `data-state="success"` или `"error"`: при успехе в нём текст благодарности, при ошибке — тексты ошибок полей через пробел, или `error`, или запасной текст. Поля из `errors` получают `aria-invalid="true"`.

```js
form.addEventListener('formgate:success', (e) => {
  // e.detail = { ok: true } — тело ответа из раздела 8; показать «Спасибо»
});
form.addEventListener('formgate:error', (e) => {
  // e.detail = { code, error, errors } — тело ответа из раздела 8
  // или { code: 'network_error', error } — ответ не пришёл (раздел 8, «Коды ошибок»)
  // или { code: 'queued_offline', error } — заявка ждёт в офлайн-очереди
});
```

### Тексты формы и офлайн-очередь

Атрибуты на `<form data-formgate>`; без атрибута остаётся текущий текст.

| Атрибут | Что делает |
| --- | --- |
| `data-formgate-success-text` | Текст в `[data-form-status]` после успеха |
| `data-formgate-error-text` | Общий текст ошибки: ответ без ошибок полей и без `error`, а также сбой сети. Тексты ошибок полей от сервера показываются как раньше |
| `data-formgate-queued-text` | Текст, когда запрос ждёт в офлайн-очереди (`queued_offline`) |
| `data-formgate-outbox="off"` | Выключает офлайн-очередь формы: при сбое сети ничего не пишется в `localStorage`, форма показывает текст ошибки с кодом `network_error`. Очередь других форм работает. По умолчанию очередь включена |

### Правила полей из npm-клиента

`formgate/client` отдаёт правила, которые проверяет сервер (источник один — файл `lite/src/Settings/field-rules.json`):

```js
import { rules, checkPhone, checkEmail } from 'formgate/client';

rules.phoneDigitsMin; // 10
rules.phoneDigitsMax; // 15
rules.maxValueLength; // 10000
rules.maxFields; // 100
rules.maxMetaFields; // 50
rules.maxMetaValueLength; // 2000
rules.maxBodyBytes; // 102400
checkPhone('+7 (999) 123-45-67'); // true: число цифр в диапазоне
checkEmail('a@b.ru'); // true: адрес по синтаксису сервера, в домене есть точка
```

`checkEmail` повторяет синтаксис PHP `filter_var(FILTER_VALIDATE_EMAIL, FILTER_FLAG_EMAIL_UNICODE)`: кириллица допустима только до `@`, домен — ASCII или punycode (`anna@xn--e1afmkfd.xn--p1ai`, не `anna@пример.рф`).

Пустая строка для `checkPhone('')` и `checkEmail('')` даёт `false`. Сервер пустой телефон или email не проверяет: пустоту ловит проверка обязательных полей. Для необязательного поля вызывайте проверку только для непустого значения.

## 7. Капчи нет

Защиту дают honeypot, проверка домена, лимит частоты и метка времени.

## 8. Ответ шлюза

### Отправка через JS (клиент formgate, `fetch` с `Accept: application/json` или JSON в теле)

Успех — `200`:

```json
{ "ok": true }
```

Ошибка:

- `code` — машинный код из таблицы ниже;
- `error` — общий текст для посетителя;
- `errors` — ошибки по полям: имя поля → текст. Есть только у ошибок проверки.

```json
{
  "ok": false,
  "code": "validation_failed",
  "error": "Проверьте поля формы.",
  "errors": { "phone": "Проверьте телефон: в номере должно быть от 10 до 15 цифр." }
}
```

### Проверки на сервере

**Обязательные поля.** Форма перечисляет их в `__required`. Атрибут `required` у поля браузер проверяет и без JS, а `__required` нужен, чтобы пустую заявку не прислал бот или ручной запрос. Оператор может задать обязательные поля и в настройках: для всего проекта (`project.required`) и для частного случая (`required` у случая, в Lite — в `cases`). Шлюз проверяет сумму трёх списков: поля проекта, поля подошедшего случая и поля из `__required`. Форма может добавить к этому списку поля, но не может убрать из него ни одного. Не хватает поля — `422 validation_failed` с этим полем в `errors`.

Остальные проверки — только для известных полей и только если они пришли:

| Поле | Проверка |
| --- | --- |
| `phone` | от 10 до 15 цифр |
| `email` (или поле из `__replyto`) | синтаксис адреса |
| любое | длина в пределах раздела 2 |
| `consent` | галочка стоит (раздел 4) |

### Обычная HTML-форма без JS

- **Успех** — `303` на `__redirect`, иначе на страницу «спасибо» из настроек проекта.
- **Ошибка** — `303` на страницу ошибки из настроек проекта с параметром `?formgate_error=<code>`.
- **Pro, неверный ключ проекта** — JSON-ответ `404 project_not_found` без перенаправления: без проекта шлюз не знает его страницу ошибки.

### Коды ошибок

| HTTP | `code` | Когда | Что делать сайту |
| --- | --- | --- | --- |
| 403 | `origin_not_allowed` | Домен не в списке проекта (и для заявки, и для `GET ?token`) | Попросить оператора добавить домен |
| 404 | `project_not_found` | **Только Pro:** неверный ключ проекта; заявка не сохраняется | Проверить адрес |
| 413 | `payload_too_large` | Превышены ограничения раздела 2 | — |
| 405 | `method_not_allowed` | Запрос не методом `POST` (кроме `OPTIONS` и `GET ?token`, раздел 6) | — |
| 415 | `unsupported_media_type` | Неподдерживаемый формат тела | — |
| 422 | `validation_failed` | Не прошла проверка на сервере: телефон, email, длина | Показать ошибки у полей из `errors` |
| 422 | `consent_required` | Нет галочки согласия | Показать ошибку у галочки |
| 500 | `delivery_failed` | **Только Lite:** заявку не принял ни один канал | «Не удалось отправить, попробуйте позже» |
| 500 | `server_error` | Внутренняя ошибка | То же |
| — | `network_error` | **Только клиент:** ответ шлюза не пришёл (нет сети, таймаут, не JSON). Шлюз этот код не отдаёт | Показать запасной текст, предложить отправить ещё раз |

**Молчаливые отказы.** На признаки бота шлюз отвечает **успехом**, а заявку не доставляет, а кладёт в спам-лог с причиной. Признаки бота: заполнен honeypot, нет заголовка User-Agent, превышен лимит частоты, а с включённой проверкой метки — нет действительной метки (причины — в разделе 6, «Метка времени»). Одинаковая заявка в той же форме в течение 10 минут тоже получает «успех», но второй раз не доставляется. Поэтому «успех» не гарантирует доставку. Если тестовая заявка не дошла, попросите оператора посмотреть спам-лог.

**Pro и доставка.** В Pro «успех» означает, что заявка сохранена: шлюз отвечает сразу, а в каналы заявку доставляет отдельный процесс через несколько секунд. Поэтому `delivery_failed` в Pro не бывает. Если канал временно недоступен, шлюз дошлёт заявку сам. Отправлять её повторно не нужно.

## 10. Чек-лист перед запуском
